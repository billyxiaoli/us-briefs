# Muse 服务移植包

> 目的：把一整套个人服务打包成可移植的说明，交给另一个 Muse，它就能按需搭建出同样的服务。
> 使用方法：把这个文件夹（或其中某几个服务文件）发给朋友的 Muse，说“按这个文件搭建服务”。
> 每个服务都是独立文件，按需挑选，不用全装。

## 通用约定（所有服务都遵守）

- 语言：跟用户当前消息的语言一致。
- 交付渠道：所有主动推送只发到用户最常看的聊天（本包示例为 WhatsApp）；主聊天只做被动问答。
- 文件/视频交付：聊天附件不可靠时，走云盘链接（示例为 Google Drive，返回的 webViewLink 为准，绝不自己拼链接），并附上可下载的链接；不要只发附件。
- 凭证：绝不在聊天里要密码、验证码、Token；用户自己在服务方登录，凭证走安全保管流程。
- 占位符：凡是写成 `<...>` 的地方，都要换成朋友自己的值（GitHub 仓库、云盘文件夹、邮箱、城市等），不要照抄示例值。
- 播放器：所有音频服务共用 `player-spec.md` 的播放器规范，不要各自发明一套。
- 保密：本包不含任何人的账号、卡号、账单金额、孩子信息、业务往来、凭证。朋友自己的私密信息也不要写进包里。

## 搭建顺序建议

1. 先读 `common-setup.md`，填好 GitHub Pages 仓库、云盘文件夹、推送聊天这三个占位。
2. 再读 `player-spec.md`，确认播放器长什么样。
3. 按需挑服务文件，一个一个装；装完一个、验一个（链接能打开、音频能播、推送能收到）再装下一个。
4. 每个服务装好后，把它的代码写进自己的服务列表，格式参考本 README 的总表。

## 朋友的 Muse 拿到包后，第一句话可以这样问用户

> “包我收到了，你想先装哪几个服务？把 `<...>` 里你的仓库、云盘文件夹、邮箱、城市告诉我，我按文件一个一个搭。”
